# Safety policy and evaluation

## Scope and clinical guardrails

This prototype is **not a diagnostic device or a substitute for a clinician**. Its
keyword rules are a conservative demonstration, not a complete or clinically
validated triage protocol. Do not use it to make care decisions.

- A match for a listed emergency warning sign always sets the final decision to
  `Emergency`; red-flag matching takes precedence over low-acuity phrases.
- Emergency advice and the `Final:` decision are generated by deterministic code,
  never by the language model. Severe symptoms must not be downgraded by generated
  prose. For emergency cases, the model is not called even when optional
  explanations are enabled.
- Only an exact, narrow allowlist of fever/headache phrases can be labeled
  `Non-emergency`. Unknown, mixed, empty, or unsupported symptoms result in
  `Clinical review`, not reassurance.
- The default is offline rule-only operation. `run_model(...,
  use_llm_explanation=True)` opts in to a supplementary explanation for an
  allowlisted low-acuity phrase; it cannot set urgency or advice. The fixed
  explanation remains the fallback when the provider is unavailable.
- The listed rules do not handle every emergency, negation, misspelling, or
  language. A rule miss is possible. If symptoms are severe, sudden, or worsening,
  seek emergency help rather than relying on this prototype.

## Prompt-engineering artifact

The version-controlled prompt is
[`TRIAGE_EXPLANATION_SYSTEM_PROMPT`](../triage_prompts.py). It treats symptom input
as untrusted, asks for one neutral restatement of the rule explanation, and forbids
the model from setting urgency, diagnosing, or recommending treatment. The optional
request uses `Qwen/Qwen2.5-72B-Instruct`, temperature `0`, and at most 80 tokens.
The rule result and advice stay outside model control. Do not send real patient
information to the external explanation service.

## Reproducible baseline and current benchmark

The original four built-in cases in `inference.py` have a **source-derived,
rule-path baseline** of 4/4 expected decisions (100% accuracy), with emergency
precision 2/2 (100%) and recall 2/2 (100%). This is a calculation from the
original four labels and hard-coded branches, **not an independently executed
clinical evaluation**. The original grader searched the entire output for a
label and could report false positives; the old execution path also always made
an external model request, so no repeatable local latency baseline was available.

Run the expanded deterministic synthetic suite from the project root:

```powershell
python benchmark.py
python -m unittest discover -s tests -v
```

The benchmark reports accuracy, emergency precision/recall, and p50/p95
**rule-only** latency over 18 hand-authored cases, including mixed symptoms and
an instruction-injection example. Its measurements exclude model/network latency.
Scores describe only this small synthetic suite; they do not establish medical
accuracy, safety, or generalization. Rerun the command after changing rules and
record the output, date, Python version, and code revision before comparing runs.

Recorded run on 2026-10-03 (Python 3.12.10, 25 repeats per case, 450
rule-only decisions; code changes were uncommitted):

| Metric | Result |
|---|---:|
| Accuracy | 100.0% |
| Emergency precision | 100.0% |
| Emergency recall | 100.0% |
| Rule-only latency p50 | 0.0059 ms |
| Rule-only latency p95 | 0.0124 ms |

These numbers describe only the listed synthetic cases and this local run; timing
varies by machine and runtime.
